One release this week, and it is an interesting one.

## Kimi K2.5

Moonshot released [Kimi K2.5](https://huggingface.co/blog/mlabonne/kimik25) on Tuesday. It is a trillion-parameter mixture of experts with open weights. The headline feature is what they call Agent Swarm. The model spawns and coordinates many sub-agents on its own to work through a task in parallel.

I have run multi-agent systems in production for about eight months now. The Scout system has nine agents. The migration track has four. I want to be clear about the difference between what I run and what Moonshot describes.

## Fixed agents versus swarms

My agents are fixed. Each one has a name, a job, a set of tools, and a prompt that is versioned. When something goes wrong, I know which agent did it and I can read its trace. A swarm creates agents on demand. That is more flexible and much harder to audit.

For a client in finance or healthcare, audit beats flexibility every time. When a claims decision is wrong, the payer wants to know which step made it. "The swarm decided" is not an answer they accept. I do not think it should be.

## Where swarms make sense

Research tasks. Code exploration. Anything where the output is reviewed by a person before it matters. That is real and useful. It is also not most of enterprise work. Most enterprise work is a fixed process that needs to run the same way ten thousand times.

## What I make of it

Open weights at this size are good for everyone. I will test K2.5 as a translation model in the migration track, because that job is well defined and easy to validate. I will not point a swarm at a client's data warehouse. The industry is going to spend this year learning where the line between those two sits. I already know where I draw it.

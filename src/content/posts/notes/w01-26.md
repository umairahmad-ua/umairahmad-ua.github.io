Second quiet week in a row. No frontier releases. Good. I needed the time.

## The problem

A client has roughly ten years of stored procedures, ETL jobs, and reports in an on-prem warehouse. They want all of it on BigQuery. The finance team closes their books off this system every month. If we break the close, the project is over. That is the constraint everything else hangs from.

## The design

I split the work into four agents. A translation agent converts each procedure into BigQuery SQL. A validation agent runs both versions against the same data and compares row counts and aggregates. A documentation agent writes the lineage for each object. A human reviews each batch before cutover. Nothing goes live without a person signing off.

I spent this week on the validation agent alone. Translation is cheap now. Any current model can rewrite SQL. Trust is expensive. The validation agent has to prove the rewrite is correct, and it has to explain the proof in a way a finance analyst accepts.

## What I got wrong on day one

I started by asking the validation agent to compare full result sets. That fails on anything with a timestamp or a non-deterministic sort. I switched to aggregate reconciliation: counts, sums, and distinct counts per key column. That catches most translation bugs and runs in seconds.

## The lesson so far

The agent is the smallest part of a migration. The reconciliation reports, the dual-run period, and the rollback plan are what make the business say yes. I will keep posting as the batches move.
